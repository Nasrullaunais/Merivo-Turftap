# Deployment

## v1 setup

One VPS (a rented server) running Docker Compose:

| Service | Notes |
|---|---|
| `caddy` | The only thing open to the internet (ports 80/443). HTTPS for `turftap.lk`, `console.turftap.lk`, `api.turftap.lk`, `n8n.turftap.lk` and the wildcard `*.turftap.lk` for tenant portals. A wildcard certificate needs the DNS challenge, which needs Caddy built with our DNS provider's plugin. |
| `api` | One image of the backend. Also runs the pg-boss jobs. |
| `portal`, `console` | Built static files, served by Caddy |
| `postgres` | Two databases: `turftap` (app) and `n8n`. Named volume. |
| `seaweedfs` | Files over the S3 protocol. Named volume. |
| `n8n` | The Assistant. Its editor is behind Caddy with basic auth. |

- Published ports other than Caddy's bind to `127.0.0.1` only.
- Every volume is **named**, never anonymous, so recreating a container can't silently start an empty database.
- `restart: unless-stopped` on every service.
- `compose.yaml` in the repo is for local development: Postgres (`127.0.0.1:5433`, with `turftap`, `turftap_test` and `n8n` databases), SeaweedFS (`127.0.0.1:8334`) and n8n (`127.0.0.1:5679`). These ports avoid clashing with other projects on the default ones; each can be changed in `.env`. The production file adds Caddy and the app images.

## Config and secrets

- All settings are environment variables, read into **one typed config object** and checked by Zod at startup.
- Every setting is listed in `.env.example`. Secrets have no default: a missing secret stops the app from starting.
- `.env` is never committed. Treat a secret that ever touched a repo or a chat as leaked and replace it.

## Auth0

Sign-in uses Auth0's passwordless SMS connection ([ADR 0008](../adr/0008-phone-login-for-everyone.md), [ADR 0010](../adr/0010-login-codes-fall-back-to-sms.md)). Set up once per Auth0 tenant:

1. **Authentication > Passwordless > SMS**: code length 6, expiry 180 seconds (`SIG-01`), and turn on **Use Tenant-level Messaging Provider**.
2. **Branding > Phone Provider > Custom**, delivery method Text: paste [`infra/auth0/custom-phone-provider.js`](../../infra/auth0/custom-phone-provider.js) and add the secrets `API_URL` (`https://api.turftap.lk`) and `HOOK_SECRET` (the API's `AUTH0_HOOK_SECRET`).
3. Relabel the resend link on the code screen to "Didn't get it? Send by SMS" (custom text for the passwordless SMS prompt).
4. Check how many wrong codes Auth0 accepts before asking for a new one. `SIG-01` asks for 3.

## Database changes

- Migrations are plain SQL files in `apps/api/migrations/`, generated by `drizzle-kit` (`bun run db:generate`) and then read by a person before committing. `bun run db:migrate` applies them ([ADR 0009](../adr/0009-drizzle-migrations.md)).
- Migrations change structure only. Demo data lives in seed scripts that are safe to run twice.
- Migrations run as **their own step** before the new version starts, never on app start-up.
- Removing or renaming a column takes two releases: first stop using it, then drop it.

## Releases

1. A pull request merges into `main` after CI passes (lint, type check, all tests).
2. Tag `vX.Y.Z`. CI builds and pushes the images.
3. On the server: back up → migrate → start the new version → check `/health/ready`.

## Backups

- Nightly `pg_dump` of both databases and a copy of the SeaweedFS data, sent to off-site storage.
- A restore is tested once a month. An untested backup doesn't count.

## Watching it

- JSON logs with a `requestId` on every line. The same id is returned as `traceId` in errors, so a user's screenshot leads straight to the log.
- `/health` (the process is up) and `/health/ready` (the database is reachable).
